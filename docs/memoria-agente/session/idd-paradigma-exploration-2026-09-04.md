## Key Conceptual Claims Extracted

### From "documento_mestre_paradigma_intencional.md"
- Intenção humana leaves periphery, becomes central artefact
- Domínio leaves documentation, becomes operational layer
- IA becomes disciplined operational mediation (not improvisation)
- Two-layer architecture: conventional + intention-oriented
- Ergonomia semântica: reduce mental effort to transform intention to correct action
- 7-step interaction pattern: formulação → ancoragem → restrição → resposta → complemento → execução → continuidade

### From "plano_manifesto_paradigma_idd.md"
- **Three fundamental principles**:
  1. Intenção = primary human artefact (not stories/tasks/sprints)
  2. Documentation generated by agents (not authored pre-hoc)
  3. Humans supervise upstream (goals/constraints) and downstream (validation)
- **Anatomy of intention**: WHY (business motivation), WHAT (Gherkin Given-When-Then), HOW (numbered steps)
- **Change in fundamental question**: from "How should we build this?" to "What result do we want, what constraints apply?"

### From "IDD-knowledge-base.md" (Sections 1-3)
- **Essential properties**:
  - NL as primary source (not documentation about code; specification of code)
  - Persistent governance (intent versioned with system, not discarded)
  - Human epistemic command (what/why)
  - Augmenting ≠ Automating
  - Auditability (all actions traceable to intent)
  - Business invariants as salvaguards

- **2.1: Epistemic vs Operational Command** (Eliezer's distinction):
  - Epistemic: authority over what/why, intent, constraints, success criteria, ethical limits
  - Operational: authority over how, tools, syntax, execution sequence
  - Foundational principle from Engelbart 1962
  - Contrast: Credulity (trust without evidence) vs. Bayesian faith (trust by audit)

- **2.5: DAV (Deterministic Action Vocabulary)**
  - LLM never interprets domain data — only interprets intention
  - 4-layer architecture: fast-path regex → LLM intent mapping → deterministic handler → raw data
  - Prevents LLM hallucination by design
  - Materializes epistemic/operational distinction in data handling

- **Linhage**: Bush (1945 Memex) → Licklider (symbiosis) → Engelbart (augmentation 1962) → Sutherland (Sketchpad) → Kay (Dynabook) → Brooks (conceptual integrity) → Knuth (literate programming) → Evans (DDD 2003) → North (BDD 2006) → Karpathy (vibe coding 2025)

- **Vibe Coding**: antithesis of IDD — trusts IA without understanding, used in disposable projects and YC startups (25% of YC Winter 2025 had 95% AI-generated code)

## Extensions from Stockley's Six Elements

The Eliezer formulation extends Stockley's IDD (from his ebook) with:
1. **Epistemic vs. Operational command** — Not in Stockley; Eliezer's synthesis from Engelbart
2. **Persistent governance layer** — Intent versioned with code (Stockley: one-time spec)
3. **DAV (Deterministic Action Vocabulary)** — Eliezer's architectural pattern to prevent LLM hallucination
4. **Genealogical framing** — IDD as continuation of 80-year augmentation tradition (Bush→Engelbart)
5. **Invariants as salvaguards** — Business rules in intent, not negotiable, enforced by system
6. **Confirm-Once pattern** — Single approval + agent execution (governance at boundary, not per-step)
7. **Ergonomia Semântica** — Reducing cognitive impedance between user intention and system action (systems theory)

## Divergences from Stockley
- Stockley: WHY/WHAT/HOW as one-time spec → Eliezer: NL as persistent layer, continuously validated
- Stockley: Spec → Code → Done → Eliezer: Intent → Agents ↔ Code (bidirectional, ongoing)
- Stockley: Focus on reduction of developer work → Eliezer: Focus on augmentation of human thinking
