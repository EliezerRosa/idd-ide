Tópico 1 · Fundamentação Histórica

Objetivo e Contexto do Paradigma IDD

A linguagem natural como fonte primária e a linhagem intelectual de 80 anos
Eliezer Rosa (2026)

⬡ A Inversão Ontológica do Software 🔭 tese

No desenvolvimento tradicional, o código-fonte em disco é a verdade soberana. A intenção original do arquiteto evapora em reuniões, chats e tickets desatualizados, gerando entropia contínua (Drift).

O IDD inverte a pirâmide:

  • Intenção (Track Cognitivo): O artefato primário e duradouro, expresso em linguagem natural ubíqua.
  • Código (Sombra Determinística): Mero subproduto gerado por agentes, encarado como o "novo Assembly" — não-editável manualmente.
  • Governança Contínua: O compilador de intenções monitora o alinhamento em tempo real no editor e no CI.
"A intenção humana expressa em linguagem natural é o artefato de mais alta ordem. O código existe exclusivamente como sua projeção auditável."

📜 Linhagem de 80 Anos (1945 → 2026)

  • 1945 — Vannevar Bush: O Memex e a organização do saber por trilhas associativas do pensamento.
  • 1960 — J.C.R. Licklider: Man-Computer Symbiosis — o humano define o quê e avalia; a máquina executa o como.
  • 1962/68 — Douglas Engelbart: Augmenting Human Intellect — a sofisticação da ferramenta molda a capacidade do pensamento.
  • 1984 — Donald Knuth: Literate Programming — programas expostos na ordem da mente humana, não do compilador.
  • 2003 — Eric Evans (DDD): A Linguagem Ubíqua e os Bounded Contexts.
  • 2025/26 — Karpathy: Vibe Coding e a crise da perda de controle.
O IDD não é modismo de IA: é a maturação lógica da tradição de simbiose cognitiva homem-máquina.
Tópico 1 · Axiomas Conceituais

As Distinções Fundamentais do IDD

Comando Epistêmico vs Operacional, Augmenting ≠ Automating e Fé Bayesiana
Epistemologia IDD

1. Comando Epistêmico

Quem detém: Exclusivamente o Humano.

Autoridade sobre o quê e por quê. Define:

  • Intenção do negócio
  • Invariantes e restrições éticas
  • Critérios de aceite (Given/When/Then)
  • Aprovação de waivers temporários
Abdicar do comando epistêmico é credulidade; governar com evidência é Fé Bayesiana.

2. Comando Operacional

Quem detém: Delegado ao Agente de IA.

Autoridade sobre o como. Gerencia:

  • Sintaxe de código e tipos locais
  • Scaffolding de arquivos
  • Geração mecânica de suítes de teste
  • Execução de queries determinísticas
A máquina opera sob o padrão Confirm-Once: plano aprovado uma única vez, execução integral auditada.

3. Augmenting ≠ Automating

Automatizar (Automating):

Remove o humano do circuito. Cria código órfão que ninguém compreende e ninguém pode auditar.

Augmentar (Augmenting):

Amplifica a mente do arquiteto. O software permanece como uma extensão direta, deliberada e transparente de sua intencionalidade.

Inspirado diretamente na tese de Douglas Engelbart (1962).
Tópico 1 · Princípio Arquitetural

DAV — Deterministic Action Vocabulary ✅ em produção no RVM

O LLM nunca interpreta dados — dados pertencem ao código determinístico
DAV Specification

⬡ O Problema Fatal que o DAV Elimina

Conectar LLMs diretamente a bancos de dados ou injetar dados brutos no prompt gera desastres conhecidos:

  • Alucinação factual: Criação de dados e IDs inexistentes.
  • Custo insustentável: Milhares de tokens gastos para queries triviais.
  • Inconsistência estocástica: Respostas diferentes para a mesma pergunta.
Invariante Central do DAV: "O LLM nunca é intérprete de dados — é intérprete de intenção."
// Resposta do LLM via DAV (Zero dados de banco): { "actionType": "QUERY_PUBLISHER_ELIGIBILITY", "params": { "publisherId": "p-892", "role": "DISCURSO" } }

⚙️ A Arquitetura em 3 Camadas do DAV

  • Camada 0 — Fast-path Pré-LLM: Reconhece comandos frequentes via Regex e lookup determinístico no cliente. Zero tokens gastos.
  • Camada 1 — Intent Mapping: Quando o fast-path não casa, o LLM recebe a frase e devolve apenas { actionType, params } em JSON puro.
  • Camada 2 — Action Handler Determinístico: Código nativo TypeScript executa a busca no banco e formata o resultado com garantia matemática de exatidão.
Implementado com sucesso no RVM Designações (9 handlers e 7 famílias regex) e no núcleo do IDE IDD.
Tópico 2 · Análise Comparativa

Similaridades e Contrastes no Ecossistema

Como o IDD transcende Vibe Coding, BDD, DDD, Literate Programming e Assistentes Modernos
Matriz Comparativa

⚡ O Contraste Vital com o Vibe Coding

O Vibe Coding (Palavra do Ano 2025) propõe *"esquecer que o código existe e confiar nas vibrações"*.

O Custo Oculto do Vibe Coding:

  • 2.74x mais vulnerabilidades de segurança (Veracode 2025).
  • Code churn quase duplicado e duplicação quadruplicada (GitClear).
  • O desenvolvedor se torna refém de um código que não compreende.
O IDD é a cura do Vibe Coding: mantém a interface expressiva em linguagem natural, mas adiciona comando epistêmico, invariantes e AST hard gates.

📊 Comparativo com Outros Paradigmas

  • BDD (Gherkin): O BDD usa linguagem natural apenas para testes. O IDD transforma a intenção no driver de governança de arquitetura, mutação de estado e dados.
  • DDD (Eric Evans): O DDD traduz linguagem ubíqua para classes OOP. O IDD mantém a linguagem ubíqua como artefato de primeira classe no ubiquitous-dictionary.json.
  • Literate Programming (Knuth): Knuth exigia que o humano escrevesse o código manual embutido. No IDD, o agente deriva a Sombra sob supervisão.
  • Cursor / Devin / Cline: São assistentes reativos com regras soltas. O IDD traz um ciclo de vida governado, Git bimodal e armazenamento relacional de versões de intenção.
Tópico 3 · Intenções Extraídas

As Intenções do Projeto IDE IDD ✅ Fase 0 + dicionário · circunscrição parcial

Camada 1 (Projeto & Dogfooding), Camada 2 (Arquitetura) e Camada 3 (Circunscrição v2)
project.intent.yaml

Camada 1 — Projeto

Auto-Governança do Repositório:

  • 5 Bounded Contexts declarados (core, cli, extension, ui-extension, pwa).
  • Isolamento de dependências via allowed_dependencies.
  • Políticas de fase (30 dias em exploratório, 14 em consolidação, 7 em produção).
  • Papéis formais: só o architect aprova waivers.

Camada 2 — Domínio

Um Núcleo, Dois Alvos:

  • Todo o motor IDD vive em @idd/core.
  • Alvo A: Extensão VS Code distribuída via Open VSX.
  • Alvo B: Fork dedicado do Code-OSS com shell customizado.
  • Dicionário Ubíquo determinístico validado na digitação (Layer 0 DAV).

Camada 3 — Circunscrição v2

Contrato Ancorado em Método:

version: "2.0" target_class: "Auth.UserAccount" target_method: "registerFailedLogin" behavioral_contract: state_mutation: allowed_fields: ["failed_attempts"] read_only_fields: ["email"]

Impede mutações inadvertidas de estado com validação direta na AST da linguagem.

Tópico 4 · Salvaguardas Inegociáveis

Os Invariantes do Sistema ✅ gates no CI · parte 🔭

Salvaguardas que bloqueiam merges, commits e mutações de dados não autorizadas
Hard Gates & Enforcement

🚨 Invariantes Globais Declarados

  • G-ARCH-01 (Parser Único): Um único parser de contrato em @idd/core é consumido por CLI, LSP e UI. Ninguém reimplementa validações de intenção.
  • G-ARCH-02 (Confinamento de Contexto): Importações entre bounded contexts só ocorrem se explicitadas em allowed_dependencies. Violações encerram com exit code 1.
  • G-SEC-01 (Proteção de Segredos): Segredos nunca são ecoados em logs, saídas de terminal ou memória volátil.
Validado em 88 arquivos em milissegundos via idd verify --project.

🛡️ Invariantes do Paradigma IDD

  • A Diretriz Absoluta da Sombra: É terminantemente proibido aos desenvolvedores editar código em shadow/main. A correção é sempre feita no .intent.md.
  • Invariante do Dicionário Ubíquo: Todo conceito ou entidade deve ter definição formal (≥ 10 caracteres). Termo sem definição é "string mágica".
  • Waivers Estritamente Temporários: Waivers expiram em 30 dias em fase exploratória, 14 em consolidação e 7 em produção. Não existe waiver permanente.
  • Risk Dials com Fé Bayesiana: Os dials só relaxam mediante evidência comprovada ($\ge 95\%$ de alinhamento em dezenas de verificações).

Tópico 9 · Recomendações Estratégicas

Parecer do Agente & Roteiro de Ação opinião de agente de IA

Conselhos técnicos de alta fidelidade para potencializar o impacto do IDD no mundo
Strategic Advice

🎯 Parecer Técnico do Agente

O IDD não é cosmético. É uma proposta de método para um problema central da computação com IA: como ser rápido sem se tornar ingênuo e caótico.

Seus pontos culminantes:

  • DAV: Proteção incondicional dos dados e corte radical de custos.
  • Hard Gates Pré-Rede: O IDE apita na digitação antes de gastar qualquer token.
  • Comando Epistêmico Humano: Rejeita a subserviência passiva às máquinas.

🚀 4 Recomendações Prioritárias

  • 1. Priorizar 95% do Esforço no Alvo A (Extensão VS Code): O fork do Code-OSS acarreta um custo de rebase brutal. A extensão via VSIX entrega quase todo o valor com adoção global instantânea.
  • 2. Consolidar o Track Cognitivo (.intent.md): Adotar convenção de caminho de arquivo (ctx/Classe.metodo.intent.md) e compilar para YAML sem depender de modelos estocásticos de entropia.
  • 3. Blindar a Sombra no GitHub: Aplicar branch protection em shadow/main via API; push humano deve ser rejeitado pelo servidor com mensagem educativa do IDD.
  • 4. Transformar o LSP na Jóia da Coroa: Focar na experiência do desenvolvedor: alertas visuais ricos sublinhando mutações de estado não autorizadas enquanto digita.
