# IDD IDE v2.0 — MASTER ARCHITECTURAL SPECIFICATION & EXECUTION BLUEPRINT

---

## 1. Visão Geral e Fundamentação Histórico-Científica

### 1.1 Resumo Executivo

O **IDD IDE (Intent Driven Development)** é uma plataforma de desenvolvimento neuro-simbólica projetada para elevar a *intenção de negócio* ao status de fonte primária da verdade (*Single Source of Truth*).

A versão 2.0 expande a capacidade da plataforma, estruturando um pipeline em 3 camadas que converte especificações ambíguas em Linguagem Natural em artefatos determinísticos de código, modelos relacionais rigorosos e validações visuais multimodais, combatendo continuamente o **Stochastic Semantic Drift** (Desvio Semântico Estocástico).

---

### 1.2 Herança Histórica: Do Unisys SIM (1990) & SDM (1981) ao IDD IDE

O IDD IDE resgata e moderniza as bases da **Modelagem Semântica de Dados (Semantic Data Model - SDM)** formulada por Hammer & McLeod (1981) e implementada comercialmente no **Unisys SIM (Semantic Information Manager)** na década de 1990.

```
 [ Unisys SIM (década de 1990) ]           [ IDD IDE v2.0 (2026) ]

    Esquema Semântico (SDM)                 domain.intent.yaml (Intenção)
               │                                       │
               ▼                                       ▼  idd domain compile
    Compilador SGBD SIM                    Engine Neuro-Simbólico IDD
               │                                       │
               ▼                                       ▼
 Estuturas Físicas de Banco               schema.sql + JSONB + AST + Excalidraw

```

* **Esquema Semântico como Fonte Única:** No Unisys SIM, o desenvolvedor não definia estruturas físicas (`CREATE TABLE` ou `FOREIGN KEY`), mas sim um *Esquema Semântico Declarativo*. O IDD IDE reencarna esse princípio no arquivo `domain.intent.yaml`. O DDL SQL, schemas de validação JSONB, diagramas ER e grafos Excalidraw são apenas **artefatos derivados compilados** através do comando `idd domain compile`.
* **Restrições Semânticas Ativas:** O SIM garantia que regras de negócio fossem validadas ativamente no nível da entidade. O IDD IDE expande esse conceito para o ciclo de vida do código, interceptando violações no editor (LSP), no terminal (*pre-commit*) e no pipeline de CI/CD via GitHub Actions.
* **A Evolução Neuro-Simbólica:** Enquanto o SIM exigia entradas formais 100% rígidas e escritas manualmente, o IDD IDE integra um **Compilador de Linguagem Ubíqua (SHALA-LLM)** que aceita Linguagem Natural ambígua, mensura sua entropia e conduz diálogos de convergência até atingir a estabilidade semântica necessária para o motor simbólico estrito (Axiomas de Armstrong e Formas Normais 1NF a DKNF).

## 2. Especificação da Camada 1: Governança Macro de Projeto (`project.intent.yaml`)

### 2.1 Conceito e Objetivos

A Camada 1 reside na raiz do repositório (`/project.intent.yaml`) e define as regras arquiteturais que nenhum pacote ou módulo do sistema tem permissão para violar. Ela estabelece as fronteiras entre os *Bounded Contexts* (Evans, 2003) e define a matriz de importação autorizada.

### 2.2 Schema Completo do `/project.intent.yaml`

```yaml
version: "2.0"
project: "IDD IDE Engine"
purpose: >
  Ambiente de Desenvolvimento Integrado e CLI neuro-simbólica para verificação 
  contínua de intenções de código, schemas relacionais e topologia de arquitetura.

# Invariantes Arquiteturais Globais
global_constraints:
  - id: GC-ARC-01
    type: architecture
    severity: critical
    description: "A camada de LSP e CLI nunca deve depender exclusivamente de APIs neurais/LLM sem um fallback simbólico estático operando."
    enforcement: strict

  - id: GC-SEC-02
    type: security
    severity: critical
    description: "Chaves de API, tokens JWT e segredos de ambiente nunca devem ser persistidos no SQLite local ou expostos em logs."
    enforcement: strict

  - id: GC-PERF-03
    type: performance
    severity: high
    description: "A execução da verificação estática no pre-commit hook (idd verify) não pode exceder 2.5 segundos."
    enforcement: strict

# Matriz de Isolamento de Bounded Contexts
bounded_contexts:
  - name: "cli"
    path: "packages/cli"
    allowed_dependencies: ["core", "verifier", "domain"]

  - name: "lsp"
    path: "packages/lsp"
    allowed_dependencies: ["core", "verifier"]

  - name: "domain"
    path: "packages/domain"
    allowed_dependencies: ["core"]

  - name: "verifier"
    path: "packages/verifier"
    allowed_dependencies: ["core"]

  - name: "core"
    path: "packages/core"
    allowed_dependencies: []

# Políticas Globais de Drift para CI/CD
drift_policy:
  min_overall_score: 85%
  block_pr_on_critical: true
  fail_fast: true

```

## 3. Especificação da Camada 2: Compilador L1 & Domínio de Dados

### 3.1 Fase 1 — Compilador L1 de Linguagem Ubíqua (SHALA-LLM)

#### 3.1.1 Fundamentação Teórica

Baseado na pesquisa **SHALA-LLM (Smartly Handling Ambiguous Labels in Aligning LLMs - Wu et al., MIT Media Lab, 2026)**, que demonstra que divergências em Linguagem Natural não representam ruído descartável, mas sim a distribuição de probabilidade de interpretações humanas $p_q$.

#### 3.1.2 Algoritmo de Mensuração de Entropia e Diálogo de Convergência

Para cada entrada de intenção $q$ em Linguagem Natural, o Compilador L1 solicita a geração de distribuições verbalizadas $\hat{P}_{(q,i)}$ e calcula a **Entropia Normalizada de Shannon** $\tilde{H}(p_q)$:

$$\tilde{H}(p_q) = \frac{-\sum_{c=1}^{C} p_{q,c} \log p_{q,c}}{\log C} \in [0, 1]$$

Onde $C$ é o número de interpretações candidatas identificadas.

```
                  ┌────────────────────────────────────────┐
                  │ Entrada em LN: "Bloquear conta do usuário"
                  └───────────────────┬────────────────────┘
                                      │
                                      ▼
             [ Avaliação da Entropia Normalizada H(p_q) ]
                                      │
                   ┌──────────────────┴──────────────────┐
                   ▼                                     ▼
        Se H(p_q) <= 0.35 (Baixa)             Se H(p_q) > 0.35 (Alta)
                   │                                     │
                   ▼                                     ▼
      Gera .intent.yaml Direto             [ Diálogo de Convergência L1 ]
                                           • Exibe distribuições verbalizadas
                                           • Coleta definições do dev
                                           • Minimiza Distância JS: D_JS(P_hat, P)
                                                         │
                                                         ▼
                                           Atualiza Dicionário Ubíquo Local
                                           (.intent/ubiquitous-dictionary.json)

```

#### 3.1.3 Artefato Gerado: Dicionário Ubíquo

```json
{
  "version": "1.0",
  "terms": {
    "BloqueioTemporario": {
      "definition": "Suspensão de acesso da conta por exatamente 15 minutos motivada por 5 falhas consecutivas de senha.",
      "synonyms": ["Lockout", "TemporaryLock"],
      "bounded_context": "auth"
    }
  }
}

```

### 3.2 Modelagem de Dados e Esquema Semântico (`domain.intent.yaml`)

#### 3.2.1 Contrato Semântico do Domínio

O arquivo `domain.intent.yaml` declara o modelo conceitual, as **Dependências Funcionais (FDs)** no formato $X \rightarrow Y$ e as restrições relacionais.

```yaml
version: "2.0"
domain: "ECommerce"
module: "sales/orders"

entities:
  UserAccount:
    attributes:
      cpf: { type: "string", primary_key: true }
      name: { type: "string", nullable: false }
      email: { type: "string", unique: true }

  CustomerOrder:
    attributes:
      orderId: { type: "uuid", primary_key: true }
      userCpf: { type: "string", foreign_key: "UserAccount.cpf" }
      orderDate: { type: "timestamp" }
      totalAmount: { type: "decimal" }

functional_dependencies:
  - determinant: ["cpf"]
    dependent: ["name", "email"]
  - determinant: ["orderId"]
    dependent: ["userCpf", "orderDate", "totalAmount"]

normalization_rules:
  target_normal_form: "BCNF"
  enforce_armstrong_axioms: true

```

#### 3.2.2 Engine de Normalização Simbólica (1NF a DKNF)

O comando `idd domain normalize` aplica deterministicamente os **Axiomas de Armstrong** para calcular o fechamento de atributos $X^+$:

1. **Reflexividade:** Se $Y \subseteq X$, então $X \rightarrow Y$.
2. **Aumento:** Se $X \rightarrow Y$, então $XZ \rightarrow YZ$.
3. **Transitividade:** Se $X \rightarrow Y$ e $Y \rightarrow Z$, então $X \rightarrow Z$.

Se for identificada qualquer dependência funcional $X \rightarrow Y$ onde $X$ não seja uma superchave (violação de BCNF/3NF), o motor interrompe o pipeline e sugere a decomposição sem perda de informação (*Lossless-Join Decomposition*).

## 4. Especificação da Camada 3: Circunscrição Comportamental & Verificação AST

### 4.1 Fase 2 — Circunscrição Comportamental a Métodos de Classe

Aplica o princípio de **Design por Contrato (DbC - Bertrand Meyer)** e **Domain-Driven Design (DDD - Eric Evans)** para erradicar o *Anemic Domain Model*.

Toda intenção funcional $I_{func}$ é obrigatoriamente vinculada a **um Método de uma Classe de Negócio** (Entidade/Agregado DDD):

$$\text{IntençãoFuncional } (I_{func}) \implies \text{ClasseDeNegocio.MetodoComportamental}()$$

#### Schema de Intenção de Módulo Circunscrita (`auth/user-account.intent.yaml`)

```yaml
version: "2.0"
target_class: "Domain.Auth.UserAccount"
target_method: "registerFailedLoginAttempt"

intent: >
  Registrar uma tentativa incorreta de senha, incrementando o contador interno 
  e alterando o estado da conta para BloqueadoTemporariamente ao atingir o limite.

behavioral_contract:
  visibility: "public"
  state_mutation:
    allowed_fields: ["failedAttemptsCount", "accountStatus", "lockoutExpiration"]
    read_only_fields: ["id", "email", "passwordHash"]

constraints:
  - id: C-METH-01
    type: invariant
    severity: critical
    description: "A transição para BLOCKED_TEMPORARY só pode ocorrer se failedAttemptsCount >= 5."

  - id: C-METH-02
    type: encapsulation
    severity: critical
    description: "Mutações nos atributos autorizados só podem ser executadas pelo próprio método circunscrito."

acceptance:
  - id: A-01
    given: "Uma conta com failedAttemptsCount = 4"
    when: "O método registerFailedLoginAttempt() for executado"
    then: "failedAttemptsCount passa para 5 e accountStatus altera para BLOCKED_TEMPORARY."

```

### 4.2 Fase 3 — Engine de Verificação Estrutural de AST (`idd diff --structural`)

O comando `idd diff --structural` faz o parsing do código gerado/modificado e analisa a Árvore de Sintaxe Abstrata (AST) para validar quatro eixos estruturais:

1. **Evasão de Visibilidade (Encapsulation Leak):** Detecta se atributos marcados como `read_only_fields` possuem mutadores públicos genéricos (`setters`) ou acesso público direto.
2. **Coesão LCOM (Lack of Cohesion in Methods):** Valida se o método opera diretamente sobre os campos internos da classe declarada. Se $LCOM > \text{threshold}$, aponta que a intenção foi alocada na classe errada.
3. **Acoplamento CBO & Lei de Demeter:** Garante que o método interaja apenas com seus próprios atributos, parâmetros diretos ou objetos por ele instanciados. Bloqueia chamadas profundas e encadeadas (ex: `user.getProfile().getSettings().update()`).
4. **Princípio de Substituição de Liskov (LSP):** Impede que subclasses sobrescrevam métodos enfraquecendo as *constraints* definidas na intenção da classe pai.

## 6. Integração CI/CD & Pipeline Unificado

### 6.1 Fase 5 — Workflow GitHub Actions (`.github/workflows/idd-full-verification.yml`)

```yaml
name: IDD Full Neuro-Symbolic Verification

on:
  pull_request:
    branches: [ main, master ]

jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout Repository
        uses: actions/checkout@v4

      - name: Setup Node.js Environment
        uses: actions/setup-node@v4
        with:
          node-version: '20'

      - name: Install IDD CLI & Dependencies
        run: npm ci

      - name: 1. Camada 1 — Verificação Arquitetural de Projeto
        run: npx idd verify --project --config=project.intent.yaml

      - name: 2. Camada 2 — Verificação Relacional e Normalização
        run: npx idd domain verify --target-normal-form=BCNF

      - name: 3. Camada 3 — Verificação Estrutural de AST & Diffs
        run: npx idd diff --structural --fail-on=critical

      - name: 4. Validação Visual Multimodal (Excalidraw + VLM)
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: |
          npx idd domain render-excalidraw --out=dist/domain-model.json
          npx idd domain export-png --in=dist/domain-model.json --out=dist/domain-model.png
          npx idd domain inspect-visual --image=dist/domain-model.png --intent=domain.intent.yaml --out=dist/visual-report.json

      - name: 5. Postagem do Laudo no PR
        uses: actions/github-script@v7
        with:
          script: |
            const fs = require('fs');
            const report = JSON.parse(fs.readFileSync('dist/visual-report.json', 'utf8'));
            const body = `### ⬡ IDD Neuro-Symbolic Verification Report
            - **Visual Score:** ${report.visualScore}%
            - **Status:** ${report.passed ? '✅ PASSED' : '❌ FAILED'}
            - **Achados Críticos:** ${report.findings.length}
            
            ${report.visualSummary}`;
            
            github.rest.issues.createComment({
              issue_number: context.issue.number,
              owner: context.repo.owner,
              repo: context.repo.repo,
              body: body
            });

      - name: Enforce Quality Gate
        run: |
          node -e "
          const fs = require('fs');
          const report = JSON.parse(fs.readFileSync('dist/visual-report.json', 'utf8'));
          if (report.visualScore < 85 || !report.passed) {
            console.error('Quality Gate Failed: Score abaixo do limite de 85% ou falha crítica.');
            process.exit(1);
          }
          "

```
